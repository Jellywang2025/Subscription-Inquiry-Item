# Codex 与 DSH 协作约定

1. Codex 与需求方确认公开行为、规格版本和验收编号，然后拆出能独立验收的完整流程。工单写明 Spec 提交、验收编号、依赖和范围。DSH 可调整票内技术步骤。公开行为或验收预期变化时由 Codex 和需求方更新规格。
2. 一份 Spec 有一个确定的分支和一个面向 main 的 PR。implement 完成一票，implement-spec 按依赖调度同一个 implement 流程。先找既有分支及 PR，第一份候选提交后开草稿。串行逐票提交。有并行需要时从 Spec 分支建立工单工作树，汇入前核对实际合并结果。
3. 每票在实现前由 codex-tester red 写公开入口的契约测试并记录基线。确认缺失行为造成预期失败后固定测试交接提交。ALREADY_PASSES 须带真实覆盖证据，BLOCKED 需要明确原因。
4. DSH 实现和自测，在干净候选树完成 [OCR 首扫](../../docs/agents/open-code-review.md)，处置发现后由新的 codex-tester verify 会话独立验收固定 SHA。若产出变化，对影响范围重跑测试及 OCR，再复验候选。
5. 逐票提交红灯、实现、自测、OCR 与独立验收摘要。验收通过的票标记已验收待合入，依赖者可以继续。全部票就绪后核对最终候选与逐票证据，差异、基线或规则有变化时对影响范围复扫及复验。整份 PR 通过必需检查后合入 main，关闭关联的子 Issue。
6. 完整日志留本机，公开工单和 PR 引用经过脱敏的命令结果、公开 SHA 和证据摘要。记录可见的阶段耗时、token 和返工次数。缺失指标写明未记录。
